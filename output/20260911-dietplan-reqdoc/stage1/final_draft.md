# 健康饮食方案小程序软件开发需求文档

| 项目名称 | 健康饮食方案小程序（均衡抗炎方案） |
|---------|---------|
| 文档版本 | V1.0 |
| 编写日期 | 2026-09-11 |
| 文档状态 | 需求评审中 |
| 技术栈 | 微信小程序原生 + ASP.NET Core 8 Web API + SQL Server + Vue 3 管理后台 |

## 1. 项目概述

### 1.1 项目背景

参照竞品（均衡抗炎饮食方案类小程序）的交互形态，开发一款健康饮食方案小程序。核心玩法是：运营方在后台配置"分阶段饮食方案"（如 4 个阶段、每阶段若干周、每天早中晚三餐的菜品组合），用户在小程序内按阶段、按天查看营养食谱，查看每道菜的制作方法，不满意可一键更换同类菜品，并完成每日餐食打卡，形成"方案消费 + 打卡坚持"的健康饮食闭环。

### 1.2 项目目标

1. 搭建完整的前端四级页面框架与后端内容管理能力，内容（文案、图片、方案结构）全部支持后台维护，无需发版即可更新。
2. 实现用户打卡记录与基础统计，为后续运营（连续打卡、提醒、复购转化）打基础。
3. 系统轻量起步：一期聚焦内容展示与打卡，不做电商、社交、支付。

### 1.3 本期范围

- 包含：小程序 C 端四级页面、微信授权登录、打卡记录与统计、后台内容维护（方案/菜品/图片全量可配）。
- 不包含（后续迭代）：支付与商城、社区互动、智能推荐、消息推送、多租户。

## 2. 用户角色

| 角色 | 说明 | 主要操作 |
|------|------|---------|
| C 端用户 | 微信授权登录的普通用户 | 浏览方案、查看食谱与制作方法、更换菜品、餐食打卡、查看个人记录 |
| 管理员 | 运营/内容维护人员 | 登录后台，维护方案、阶段、天、餐次、菜品、食材、步骤、图片，查看打卡统计 |

## 3. 整体页面结构（四级页面 + 底部 Tab）

小程序底部 Tab 固定 4 个：**首页、方案、视频秀、我的**（方案为默认主 Tab，"视频秀"可挂"上新"角标）。

四级页面层级如下：

| 层级 | 页面 | 说明 |
|------|------|------|
| L1 | 方案列表页（Tab：方案） | 按阶段分组展示周卡片，入口"查看方案" |
| L2 | 阶段详情 · 每日食谱页 | 天选择器 + 早/中/晚餐菜品卡片 + 打卡操作 |
| L3 | 菜品制作解析页 | 菜品大图、食材清单、分步制作说明 |
| L4 | 更换菜品页 | 搜索同类候选菜品，单选后确认替换 |

页面流转：`方案列表(L1) → 选某周 → 每日食谱(L2) → 点"查看制作方法" → 制作解析(L3)；在 L2 点"更换菜品" → 更换菜品(L4) → 确认更换 → 回写 L2`。

## 4. 功能需求（C 端）

### 4.1 L1 方案列表页

- 页面标题为当前方案名（如"均衡抗炎方案"）。
- 左侧竖向"阶段导航条"（第 1 阶段 / 第 2 阶段 / 第 3 阶段 / 第 4 阶段），点击可锚点定位，滚动时高亮当前阶段。
- 每个阶段下按"周"渲染横向卡片（第 1 周、第 2 周、第 3/4 周、第 5 周……），卡片元素：
  - 周标签（左上角胶囊）；
  - 阶段主题名（如"均衡启动""胰岛平衡""肠道修整""代谢焕活"）；
  - 背景大图（后台可配）；
  - "查看方案 ›"按钮 → 进入 L2。
- 阶段与周的划分（一个阶段含几周、每周几天）完全由后台配置驱动。

### 4.2 L2 阶段详情 · 每日食谱页

- 顶部导航：返回 + 标题"代谢畅通第1阶段 均衡启动（第1周）"（格式：方案名+阶段+周，动态拼接）。
- **天选择器**：横向滚动的日期胶囊（01 第 1 天 / 02 第 2 天 / ……），点击切换当日食谱，当前天高亮。
- **营养食谱区**：
  - 区块标题"营养食谱"，右上角"今日食谱所需食材 ›"入口（汇总当天全部食材清单，便于采购）。
  - 按**餐次**（早餐/午餐/晚餐，后台可配）分组，每组：
    - 餐次头：图标 + 餐次名 + "一键打卡"按钮（该餐次下所有菜品一次性打卡）；
    - 菜品卡片列表，每张卡片含：菜品图、菜品名、食材及克重摘要（如"有机黑米 20g、粳米 20g"，后台配置）、两个操作：
      - **查看制作方法 ›** → 进入 L3；
      - **更换菜品 ›** → 进入 L4（按后台配置的"可替换候选组"展示候选）。
- 底部固定操作条：**方案详情**（进入本阶段方案说明，图文富文本，后台可配）+ **餐食打卡**（当日全部餐次一键打卡）。
- 右下角悬浮"方案解读"入口（视频或图文，后台可配，一期可先挂图文）。
- 已打卡的餐次/菜品有明确的已完成视觉标识；更换菜品后当日食谱即时刷新。

### 4.3 L3 菜品制作解析页

- 顶部：菜品大图（通栏，后台可配，多图支持轮播）。
- 标题行：菜品名 + "喜欢这道菜"收藏按钮（一期仅本地记录，可后续接入服务端）。
- **食材清单**卡片：按"主要食材"分组，每个食材含名称、用量、缩略图。
- **制作步骤**卡片：步骤 1、2、3……逐条展示，每步含步骤文案（后台可配图文，步骤图可选）。
- 本页数据全部来自菜品主数据，无独立维护入口。

### 4.4 L4 更换菜品页

- 顶部搜索框："搜索您想替换的菜品" + 搜索按钮，支持按菜名/食材模糊搜索（在当前候选组内过滤）。
- 候选菜品列表：单选（radio）交互，当前菜品默认选中；每项含菜品图、菜名、食材摘要、"查看制作方法 ›"（可跳 L3 预览后再决定）。
- 底部固定"确认更换"按钮：点击后将当日该餐次对应菜品槽位替换为所选菜品，toast 提示成功并返回 L2。
- **候选范围规则**：每个菜品槽位在后台配置一个"可替换候选组"（同类型主食换主食、蔬菜换蔬菜），用户只能在候选组内更换，保证营养结构不被破坏。

### 4.5 打卡与统计

- 打卡粒度：菜品级（单菜打卡）、餐次级（一键打卡）、天级（餐食打卡全部），底层统一记录为菜品打卡明细。
- 每条打卡记录含：用户、日期、阶段、周、天、餐次、菜品、打卡时间。
- 打卡仅限当日（历史天只读浏览，不可补打卡；是否允许补打卡列为待确认项）。
- "我的"页展示：累计打卡天数、连续打卡天数、近期打卡日历（月视图）。

### 4.6 首页 / 视频秀 / 我的

| Tab | 一期范围 |
|-----|---------|
| 首页 | 运营位：banner 图（后台可配）+ 方案入口卡片 + 健康资讯列表（后台可配图文） |
| 视频秀 | 视频列表页（后台可配视频封面/链接/标题），点击播放；带"上新"角标开关 |
| 我的 | 用户信息（微信头像昵称）、打卡统计（累计/连续/日历）、收藏的菜品、关于 |

## 5. 功能需求（后台管理端）

管理后台为 Web 端（Vue 3 + Element Plus），账号密码登录，管理员角色管理。

### 5.1 内容维护（核心）

所有 C 端展示的信息与图片均可维护，层级结构为：

**方案 → 阶段 → 周 → 天 → 餐次 → 菜品槽位 → 候选组/菜品**

| 模块 | 维护内容 |
|------|---------|
| 方案管理 | 方案名、简介、状态（草稿/上线/下线）、排序 |
| 阶段管理 | 阶段名、主题名、顺序、阶段导航文案、方案详情富文本 |
| 周管理 | 周标签（第 N 周）、归属阶段、周主题、卡片背景图上传 |
| 天管理 | 每周的天数、每日三餐的菜品槽位配置（从菜品库选菜） |
| 菜品管理 | 菜名、副标题、食材及克重（结构化）、制作步骤（富文本/分步图文）、大图/轮播图上传、分类（主食/荤菜/素菜/汤品…）、状态 |
| 食材管理 | 食材名、单位、图片（可复用菜品维度） |
| 候选组管理 | 为每个菜品槽位配置可替换的候选菜品集合 |
| 素材管理 | 图片/视频统一上传，支持拖拽、预览、复用；存储至服务器或对象存储 |
| 今日所需食材 | 按天自动汇总食材清单（系统计算），支持人工微调备注 |

### 5.2 运营与统计

- 用户列表：openid、头像昵称、注册时间、最近活跃。
- 打卡统计：按日/周/月汇总打卡人数、打卡率；单用户打卡明细查询；导出 Excel。
- 方案热度：各方案/阶段的进入量统计（一期可用简单的访问计数）。

### 5.3 通用要求

- 内容支持草稿/发布双态，发布后小程序端即时生效（接口实时读取，无需审核机制）。
- 删除菜品/阶段时做引用校验（被方案引用的不可直接删除）。
- 关键操作（删除、下线）二次确认。

## 6. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 列表接口响应 < 500ms；图片走 CDN/静态资源，小程序端做懒加载与本地缓存 |
| 容量 | 一期支撑 1 万注册用户、1000 日活；并发无压力场景 |
| 安全 | 接口 JWT 鉴权；管理后台 RBAC（一期仅管理员角色）；图片上传校验类型与大小；SQL 参数化 |
| 兼容 | 微信基础库 2.30+，iOS/Android 主流机型；iPhone SE 小屏适配 |
| 合规 | 微信授权登录获取 openid，不强制获取手机号；隐私协议弹窗首次启动展示 |

## 7. 技术架构

| 层 | 选型 | 说明 |
|----|------|------|
| 小程序端 | 微信原生（WXML/WXSS/JS） | 无跨端框架，TabBar 4 页 + 各级页面 |
| 后端 | ASP.NET Core 8 Web API | Clean Architecture 分层；JWT 鉴权；RESTful 接口 |
| 数据库 | SQL Server | 内容主数据 + 用户打卡数据 |
| 管理后台 | Vue 3 + Element Plus | 独立部署，走同一 API |
| 文件存储 | 本地磁盘/对象存储 + 静态访问 | 图片统一由后台上传，返回 URL |

### 7.1 数据模型概要

| 表 | 关键字段 |
|----|---------|
| Plan（方案） | id, name, intro, status, sort |
| Stage（阶段） | id, plan_id, name, theme, sort, detail_rich_text |
| Week（周） | id, stage_id, label, theme, cover_image |
| PlanDay（天） | id, week_id, day_no |
| MealSlot（餐次槽位） | id, plan_day_id, meal_type(早/午/晚), sort |
| DishSlotItem（槽位菜品） | id, meal_slot_id, dish_id, sort |
| DishCandidateGroup（候选组） | id, name |
| CandidateGroupItem | group_id, dish_id |
| Dish（菜品） | id, name, subtitle, category, images, ingredients(json), steps(json), status |
| Ingredient（食材） | id, name, unit, image |
| User | id, openid, nickname, avatar, created_at |
| CheckInRecord | id, user_id, date, plan_id, stage_id, week_id, day_no, meal_type, dish_id, created_at |

### 7.2 接口概要（REST）

- `GET /api/plans` 方案列表；`GET /api/plans/{id}` 方案详情（含阶段/周树）。
- `GET /api/plans/{id}/days/{dayNo}/meals` 某天三餐食谱（含菜品与替换候选标识）。
- `GET /api/dishes/{id}` 菜品制作解析；`GET /api/dishes/{id}/candidates` 可替换候选列表（支持关键字搜索）。
- `POST /api/checkins` 打卡（body 含槽位与菜品）；`GET /api/checkins/summary` 我的打卡统计。
- `POST /api/auth/wx-login` 微信 code 换 openid 签发 JWT。
- 管理端 `/api/admin/*`：上述各实体的 CRUD + 上传 + 统计报表。

## 8. 迭代计划（建议）

| 里程碑 | 内容 | 验收标准 |
|--------|------|---------|
| M1（2 周） | 数据模型 + 后台内容维护 CRUD + 图片上传 | 后台能完整配出一条"4 阶段方案" |
| M2（2 周） | C 端 L1-L4 四级页面 + 微信登录 | 按截图还原交互，内容全部来自后台 |
| M3（1 周） | 打卡 + 统计 + 我的页 | 打卡记录落库，后台可查统计并导出 |
| M4（1 周） | 联调测试、体验优化、提审发布 | 微信审核通过，线上可用 |

## 9. 待确认项

1. 历史天是否允许补打卡（影响打卡规则与统计口径）。
2. "方案解读"悬浮入口一期挂图文还是视频。
3. "喜欢这道菜"收藏是否需要服务端持久化（当前按本地存储设计）。
4. 图片存储方式：自建服务器磁盘 or 对象存储（OSS/COS）。
5. 是否需要"今日食谱所需食材"的采购清单导出/分享功能。
